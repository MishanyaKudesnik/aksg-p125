# АКСГ — сайт проекта P125 «Центр управления»

Контрольно-сетевой график строительства железнодорожной инфраструктуры: план и факт по работам,
привязка к пикетажу, подтверждения факта, прогноз с каскадом задержек, работа в поле без интернета.

- Интерфейс: обычные HTML, CSS и JavaScript, без сборки.
- Сервер: функции Vercel (папка `api/`), тот же код запускается локально через `dev-server.js`.
- База: PostgreSQL. Схема создаётся сама при первом запуске (`lib/db.js`).

## Роли

| Роль | Что может |
|---|---|
| **Инспектор** | Вносит факт по работам, добавляет подтверждения, работает в поле без связи, выгружает и загружает пакеты |
| **Руководитель** | Видит весь ход работ, отклонения, каскад задержек и хронологию. Данные не меняет |
| **Администратор** | Всё то же плюс люди, роли, коды доступа и журнал действий |

Первый человек, зарегистрировавшийся в пустой системе, становится администратором.
Дальше вход только по коду приглашения: администратор создаёт код под нужную роль и передаёт его человеку.
Код на одно применение, роль заложена в самом коде — выбрать себе администратора нельзя.

## Подтверждение факта с фотографией

В окне «Подтверждение факта» сначала выбирается способ, и окно перестраивается под него:

| Способ | Что предлагает |
|---|---|
| Фото | «Снять камерой» (открывает камеру планшета) или выбрать файл; поле «Что на снимке» |
| Акт | Загрузить PDF или фотографию, обязательный номер и дата акта |
| Исполнительная схема | Загрузить файл схемы, обозначение |
| Журнал работ | Снять страницу журнала камерой, номер записи |
| Кадр с камеры наблюдения | Загрузить кадр, камера и время |
| Без файла | Запись без вложения — например, ссылка на внешнюю систему |

### Сколько весят вложения

Снимок уменьшается прямо в устройстве: сначала кадр сжимается до 1600 точек по длинной стороне, затем
подбирается качество JPEG (0,72 → 0,42), пока файл не уложится в 900 КБ. Обычно выходит 300–700 КБ
вместо нескольких мегабайт; оригинал остаётся в галерее устройства.

| Предел | Значение | Что будет при превышении |
|---|---|---|
| Фотография | 1,2 МБ | Сервер отвечает 413 и просит снять через кнопку «Сфотографировать» |
| Любой файл | 3,5 МБ | Больше не пропускает сама платформа |
| Все вложения проекта | 350 МБ (`FILES_QUOTA_MB`) | Сервер отвечает 507, загрузка останавливается |

Занятое место видно в разделе «Файлы» и у администратора: полоса, проценты и число файлов
(`GET /api/file?usage=1`). С 80 % заполнения сигнал «Требует внимания» показывает отдельный повод
«Место в хранилище», чтобы архив выгрузили заранее, а не когда подтверждения перестанут сохраняться.
Перед сохранением файла в устройстве приложение сверяется с остатком — в поле не окажется, что
снимок некуда девать.

Файл уходит в таблицу `files` базы данных, в списке подтверждений виден снимок и ссылка на оригинал.

### Архив вместо удаления

Место освобождается без потери доказательной базы. У администратора в разделе «Люди» есть «Архив вложений»:

1. Выбирается дата — выгружается всё, что загружено раньше неё (или всё сразу).
2. Содержимое собирается частями по 2 МБ (через сеть больше не проходит) и сохраняется файлами
   `АКСГ_архив_2026-11-21_частьN.json`.
3. Только после подтверждения, что файлы сохранены, содержимое в базе обнуляется: `data` пустеет,
   проставляются `archived_at` и `archive_ref`. Строка файла остаётся: имя, размер, тип, кто и когда
   загрузил, с какого устройства, когда снято и **хеш SHA-256**.
4. Освобождается место только у тех файлов, чей хеш сошёлся с выгруженным. Несовпавшие остаются в базе.

Подтверждение в графике не меняется — рядом с именем файла появляется метка «в архиве с ДД.ММ.ГГГГ».
Запрос такого файла отвечает 410 и говорит, в каком архиве он лежит, а не «не найден».

Возврат: администратор загружает файлы архива обратно, каждый проверяется по сохранённому хешу —
подменённое содержимое не встанет на место. Удаления файлов в системе нет ни в каком виде.

Без связи файл остаётся в устройстве (IndexedDB), запись помечается «файл в устройстве, уйдёт на сервер
со связью», и отправляется сама, как только интернет появится. В полевой пакет фотографии входят вместе
с правками.

## Работа в поле без интернета

1. Сайт открывается без связи: оболочка закеширована, данные берутся из устройства.
2. Инспектор вносит факт как обычно. Правки копятся в устройстве, в шапке видно «не отправлено: N».
3. Если связь не появится, на вкладке **Файлы** жмём «Пакет с моими правками» — скачивается файл
   `АКСГ_пакет_2026-11-20_login.json` с автором, устройством и датой сбора.
4. Там, где интернет есть, этот файл загружают на той же вкладке. Сервер применит правку, если она
   свежее серверной, запишет её в хронологию и отметит пакет как принятый.
   Повторная загрузка того же файла ничего не продублирует.
5. Как только связь появляется сама, накопленные правки уходят на сервер без участия человека.

Кнопка **«Правки в Excel»** собирает файл `.xlsx` с тем, что ещё не ушло на сервер: лист «Правки»
(работа, участок, пикеты, план, факт, прогноз, задержка, кто и когда вносил), лист «Подтверждения»
и лист «Сведения» с датой сбора и автором. Библиотека Excel лежит на сайте и закеширована, поэтому
файл собирается и без интернета. Эта же кнопка появляется прямо в предупреждении на дашборде, когда
связи нет.

Ещё есть выгрузка всего графика в `CSV` и полная копия базы в `JSON`.

## Сохранение

- Правка уходит на сервер через 2,5 секунды после изменения.
- Раз в 10 минут выполняется контрольная отправка, даже если ничего не менялось.
- Состояние отправки видно в шапке: «сохранено 14:05», «не отправлено: 3», «нет связи».
- Если кто-то успел сохранить раньше, сервер вернёт отказ по версии, страница подтянет свежие данные
  и повторит вашу правку поверх — чужая работа не затирается.

## Темы и устройства

Кнопка в меню переключает: как в системе → светлая → тёмная. Выбор запоминается.
Ноутбук — боковое меню и таблица с закреплёнными колонками. Планшет — рельса иконок и карточки работ
с крупными кнопками. Телефон — нижняя панель вкладок. Все кнопки не ниже 48 пикселей.

## Датчики и камеры

У оборудования свои ключи, не связанные с учётными записями людей. Администратор заводит устройство
в разделе «Люди» → «Датчики и камеры» и получает ключ (он показывается один раз).

```
POST /api/sensor
authorization: Bearer <ключ устройства>
content-type: application/json

{"work":"W2","progress":85,"ref":"cam-07 20.11 09:40","note":"ПК 40-95"}
```

Процент попадает в факт работы, источник помечается как «Камера/датчик», в хронологии видно название
устройства, а `ref` заводит подтверждение. Несколько записей за раз: `{"reports":[{...},{...}]}` —
до 200 штук, ответ разбирает каждую отдельно. Отключённое устройство получает отказ.

## Загрузка графика заказчика

Раздел «Файлы» → «Загрузить график работ» принимает настоящий «График производства работ» ДКСС,
а не только простую таблицу. Разбор (`public/import-schedule.js`) понимает:

- шапку согласования над таблицей — строка заголовков ищется по колонке «Наименование работ»;
- разделы («Раздел 1. Верхнее строение…») — становятся участками, подзаголовки уходят в примечание;
- недельную сетку: месяц объявлен один раз и тянется вправо, под ним номера недель. Из первой и
  последней заполненной недели получаются плановые сроки работы;
- клетки вида «200/400» — факт и план, и запятую как десятичный разделитель («1,2/2»);
- проектный объём, единицу измерения и выполнение — из них считается процент;
- пикетаж внутри названия работы: «ПК 125+50», «ПК 10+00 – ПК 25+50».

Перед загрузкой показывается разбор: сколько разделов и работ, за какой период, таблица первых работ
и список нестыковок — например, «выполнено 52 при проектном объёме 22 — засчитано как 100 %».
Это пометки, а не ошибки: такие расхождения в графике заказчика действительно есть, и система
их показывает, а не прячет. Дальше на выбор: добавить к текущим или заменить весь график.

Проверено на файле `fixtures/grafik-zakazchika.xlsx` (он же «График реализации объекта.xlsx»):
6 разделов, 34 работы, сроки с 08.01.2023 по 30.06.2023, у 32 работ сроки из сетки.

## Меры защиты (к разговору с экспертом ИБ)

Разобрано по документу «ИБ проекта P125» от 12.11.2026 — здесь то, что реально работает в коде.

| Обещано эксперту | Как сделано |
|---|---|
| Контроль целостности файлов по SHA-256 | Хеш считается при загрузке и хранится в `files.sha256`. При каждой выдаче файл пересчитывается и сверяется: не совпало — выдача останавливается (код 409) и в журнал пишется «подмена файла обнаружена». Хеш виден в карточке подтверждения и отдаётся в заголовке `x-content-sha256` |
| Ограничение частоты запросов | Пять неверных попыток входа по логину и двадцать с одного адреса за 15 минут — дальше отказ 429 на 15 минут. Удачный вход счётчик обнуляет. Регистрация — не больше десяти с адреса в час. Блокировки пишутся в журнал |
| Неизменяемый журнал (append-only) | Триггеры в самой базе запрещают UPDATE и DELETE для `history` и `audit`. Проверено: даже прямой SQL из psql получает отказ |
| Резервное копирование | `GET /api/backup` (только администратор) отдаёт весь проект одним файлом: график, факты, подтверждения, хронология, журнал, люди, устройства, перечень файлов с хешами. Пароли и содержимое файлов в копию не входят. Кнопка — в разделе «Люди» |
| Архив вложений вместо удаления | `POST /api/archive` (только администратор): содержимое уезжает в файл архива, строка файла с хешем остаётся. Место освобождается лишь у того, чей хеш сошёлся; возврат тоже сверяется по хешу. Удаления файлов в системе нет |
| Правка плана только с основанием | Сдвинуть плановые сроки нельзя молча: и интерфейс, и сервер требуют основание (справка ГИПа, распоряжение). Оно уходит в хронологию строкой «план: было → стало. Основание: …». Без основания сервер отвечает 400 и ничего не меняет |
| Данные подрядчика со статусом «требует проверки» | Сводка от камеры или датчика больше не становится фактом сама: она ложится в очередь на проверку. В карточке работы видно «Камера ПК 40-95: 66 % — у нас 45 %, расхождение 21 п.п.» и кнопки «Принять» / «Отклонить». Отклонение требует причины. Принимает только человек с правом записи |

Пароли хранятся как `scrypt` с солью (стандартная библиотека Node). В документе ИБ названы Argon2/bcrypt —
стойкость сопоставима, но расхождение с документом лучше либо поправить в документе, либо закрыть переходом
на указанный алгоритм.

### Три состояния подтверждения

На каждой работе одна метка, как в докладе: **подтверждено** (есть документ), **ждёт подтверждения**
(пришла сводка от оборудования, человек ещё не решил), **не подтверждено** (факт введён, документа нет).

## Уведомления

Система сама следит за четырьмя поводами: работа просрочена, отставание дотянуло до отклонения, сводка
оборудования висит без проверки больше суток, у работы есть факт без подтверждающего документа.

Уведомления живут **в самом приложении**, наружу ничего не отправляется: ни почты, ни мессенджеров,
ни сторонних сервисов. В шапке кнопка — «Требует внимания: 3 · 1 новое» или «Всё по плану». По нажатию
список по поводам; то, что человек уже видел, перестаёт быть новым; клик по строке открывает карточку
работы. Обновление при входе и каждые пять минут.

Если человек разрешит, браузер покажет сообщение на экране, когда появится новый повод, — даже при
свёрнутой вкладке. Разрешение запрашивается один раз, кнопкой в том же окне.

## Графики

Отдельный раздел **«Графики»** (`#chart`) — четыре диаграммы, всё обычным SVG, без внешних библиотек:
рисуется офлайн и печатается вместе с отчётом.

| График | Что показывает | Как считается |
|---|---|---|
| **Освоение: план, факт, прогноз** (S-кривая) | три линии на одном поле: как должно идти, как идёт, куда придём | план — средний ожидаемый процент по всем работам на каждую дату; факт — по записям хронологии; прогноз — от сегодняшнего факта до расчётной даты окончания |
| **Диаграмма Гантта** | полосы работ по времени, заливка внутри — выполненный объём, светлый хвост — прогнозный выход за план, тонкие линии — связи «после» | плановые даты, факт, прогноз движка |
| **Участки: ожидание и факт** | по каждому участку два столбца — сколько должно быть сделано и сколько сделано | среднее по работам участка |
| **Отклонение по работам** | столбцы влево и вправо от нуля: кто недобрал, кто с опережением | факт минус ожидаемый процент, в пунктах |

S-кривая вынесена ещё в два места: на дашборд (и в техническом виде, и в кабинете руководителя)
и первым разделом в оба отчёта.

**Про факт на S-кривой.** Если по работе есть записи в хронологии, линия строится по ним.
Если работу завели сразу с процентом (загрузили из Excel) и записей нет, ход восстанавливается
по её же плану, но не выше достигнутого процента — «шла по плану, пока не остановилась».
Подпись под графиком всегда говорит, сколько работ восстановлено, а сколько построено по записям:
додумывать молча нельзя.

## Работы по пикетажу: слои стройки

Раздел **«Пикетаж» → «Слои работ»** отвечает на вопрос, который команда проекта ставила в рабочем
чате: «как привязать пикетаж к КСГ так, чтобы было видно, где какие работы и где отставание».

Там же был назван и подвох: видов работ не три, а много, и если красить каждый вид своим цветом,
получится «тысяча цветов», в которой ничего не разобрать. Поэтому:

- **цветом показано состояние** — четыре цвета: в норме, риск, отставание, работ нет;
- **виды работ разнесены по строкам-слоям**, снизу вверх в порядке стройки: земляное полотно →
  искусственные сооружения → верхнее строение пути → СЦБ и связь → электрификация → прочие;
- слой можно оставить один — кнопки над лентой;
- бледная заливка отрезка — плановый фронт работы по пикетажу, яркая — выполненный объём.

Вид работы определяется по названию работы (отдельного поля в графике заказчика нет):
`lib/engine.js` → `KINDS` и `workKind()`. Что не распозналось, попадает в «прочие работы»,
а не теряется.

**Поперечник на выбранном пикете.** Клик по ленте выбирает пикет, и под ней рисуется типовая
конструкция пути: земляное полотно, балластная призма с путём, опора контактной сети, светофор СЦБ,
водопропускная труба. Каждый элемент окрашен по состоянию наших работ этого вида на этом пикете,
насыщенность — процент выполнения. Рядом список: какие именно работы затрагивают этот пикет.
Двойной клик по отрезку открывает карточку работы.

Конструкция нарисована типовой намеренно: по всей длине перегона она почти одна и та же —
это замечание заказчика из того же чата. Геология и отметки из рабочих чертежей сюда не переносятся:
показывается только то, что система знает из графика работ.

## Продольный профиль

**«Пикетаж» → «Продольный профиль»** — чертёж в том виде, в каком его привыкли читать:
сверху чёрная линия земли и красная проектная, между ними заливка (зелёная насыпь, жёлтая выемка),
снизу «подвал» с отметками. Строки подвала: проектная отметка, отметка земли, рабочая отметка
(плюс насыпь, минус выемка), уклон в тысячных с длиной участка, пикет.

Под чертежом — полоса состояния наших работ на этом месте: ради этого всё и делалось.
Профиль и КСГ на одном листе, видно не только какой здесь рельеф, но и что здесь сделано.
Выбранный в «Слоях работ» пикет отмечен пунктиром и здесь.

**Откуда данные.** Только из ведомости проектировщика: таблица с колонками **Пикет**,
**Отметка земли**, **Проектная отметка** (примечание необязательно), `.xlsx`, `.xls` или `.csv`.
Пикет понимается и как «ПК 125+50», и как число; запятая в отметках как разделитель — тоже.
Пустая клетка означает «отметки нет», а не ноль. Загрузка заменяет профиль целиком и пишется
в журнал действий. Уклоны и рабочие отметки система считает сама из этих данных и ничего не достраивает.

Пока ведомости нет, раздел показывает, что именно нужно загрузить, и предлагает кнопку
с четырнадцатью демонстрационными точками — посмотреть, как выглядит раздел. Эти точки помечены
как демонстрационные и затираются первой же настоящей загрузкой.

| Где | Что |
|---|---|
| `profile` | таблица: пикет, отметка земли, проектная отметка, примечание |
| `GET /api/profile` | отдать профиль (всем, кто вошёл); профиль приходит и вместе с графиком |
| `POST /api/profile` | заменить профиль целиком (инспектор, администратор) |
| `engine.js` | `profileRows` — разбор ведомости, `working` — рабочая отметка, `slope` — уклон в ‰, `profileSummary` — сводка |

## Два отчёта и кабинет руководителя

**Технический отчёт** (`#report`) — для инспектора и проверяющего: сводка, готовность по участкам,
работы с отклонениями и причинами, сдвиги по зависимостям, полный перечень с источником факта,
подтверждения с хешами и метаданными снимков, пояснение расчётов, подписи.

**Отчёт простым языком** (`#report-simple`) — для руководства и заказчика: то же состояние, но фразами
(«2 работы отстают настолько, что это уже отклонение…»), таблицы без технических колонок —
работа, где это, что сейчас, когда закончится, подтверждено ли.

Оба печатаются в PDF кнопкой «Печать или PDF».

**Кабинет руководителя.** Роли «Руководитель» дашборд открывается простым видом: крупная цифра
готовности, метка состояния, пять-шесть фраз о том, как идут дела, участки с одной строкой пояснения
и список того, что мешает прямо сейчас. Переключатель «Подробный вид» возвращает технический дашборд —
и наоборот, инспектор может посмотреть простой. Выбор запоминается.

## Что взято у зарубежных систем

Разбор — в `01_защита_концепции/Анализ_зарубежных_аналогов.md` (TILOS, Sablono, OpenSpace, Doxel,
PlanRadar, Capmo, Glodon). В код вошло три вещи:

- **Диаграмма «время–пикетаж»** (из Trimble TILOS, отраслевой стандарт для линейных объектов).
  На вкладке «Пикетаж» переключатель: обычная схема или диаграмма, где по горизонтали путь,
  по вертикали время. Видно, какие работы сходятся на одном участке в одно время — по Ганту этого
  не разглядеть. Серая линия — план, цветная — прогноз, красная горизонталь — отчётная дата.
- **Темп работ** (из Doxel). В карточке работы: «темп 4,1 %/день, нужно 1,8» — сколько идёт сейчас
  и сколько нужно, чтобы уложиться в плановый срок.
- **Метаданные снимка** (из PlanRadar). К фотографии сохраняется, когда она снята, с какого устройства
  и кто загрузил, — рядом с хешем SHA-256.

Сознательно не взято: распознавание по видео и BIM (заказчик отказался от видеонаблюдения и БПЛА),
связь прогресса с оплатой (нужна сметная часть), недельные и месячные планы как отдельные сущности
(перегрузит интерфейс), раздел замечаний и дефектов (другая задача).

## Схема базы

| Таблица | Назначение |
|---|---|
| `users` | Люди: логин, имя, роль, хеш пароля (scrypt), признак доступа |
| `sessions` | Сессии входа, срок 30 дней, хранятся в cookie HttpOnly |
| `invites` | Коды приглашения: роль, сколько применений осталось, кто выдал |
| `projects` | Проект и его версия (`rev`) для защиты от перезаписи |
| `sections` | Участки с границами пикетажа |
| `works` | Работы: план, факт, статус, источник, предшественники, кто и когда правил |
| `evidence` | Подтверждения факта: акты, фото, схемы, записи журнала |
| `history` | Хронология: каждое изменение факта с автором, источником и временем |
| `devices` | Датчики и камеры: название, хеш ключа, когда последний раз присылали |
| `files` | Вложения подтверждений: фотографии, акты, схемы |
| `reports` | Сводки от оборудования: ждут проверки, принято или отклонено с причиной |
| `attempts` | Счётчики попыток входа для защиты от подбора |
| `batches` | Загруженные полевые пакеты: автор, устройство, что применено |
| `audit` | Журнал действий: входы, сохранения, выдача кодов, смена ролей |

Контейнеры (Docker) для этой задачи не нужны: Vercel сам поднимает функции по запросу, а база живёт
отдельным управляемым сервисом. Контейнер понадобился бы при переезде на собственный сервер —
код от этого не меняется, нужен только адрес базы в `DATABASE_URL`.

## Запуск на своём компьютере

```
createdb aksg_p125
echo "DATABASE_URL=postgres://ПОЛЬЗОВАТЕЛЬ@localhost:5432/aksg_p125" > .env.local
npm install
npm run dev
```
Откроется на http://localhost:3000. Первый вход — регистрация, роль администратора выдаётся сама.

## Тесты

```
npm test
```

30 проверок в трёх файлах. `site.test.js` — регистрация и коды приглашения, права трёх ролей, запрет записи руководителю, конфликт
версий, полевые пакеты (применение, защита от повтора и от затирания свежих данных), вложения
(загрузка, выдача, запрет чужих типов и больших файлов, фотографии из полевого пакета), оборудование
(выдача ключа, приём процента, пачка записей, чужой и отключённый ключ), хронология и действия
администратора. `import.test.js` — разбор настоящего графика заказчика на файле-образце. Отдельно проверены все шесть мер защиты: хеш и остановка выдачи подменённого файла, блокировка подбора пароля, запрет правки журнала из самой базы, отказ при смене плана без основания, резервная копия без паролей, сводка оборудования через проверку человеком. Сервер поднимается на отдельной базе, рабочие данные не затрагиваются.

## Сайт в интернете

**https://aksg-p125.vercel.app**

Проект Vercel — `aksg-p125`. База — PostgreSQL (Neon) из каталога Vercel, бесплатный тариф,
переменная `DATABASE_URL` подставляется автоматически для production, preview и development.
Схема и демонстрационный график создались при первом открытии сайта.

Выложить обновление:
```
vercel deploy --prod --yes
```
Файлы `.env.local` (своя база для разработки) и `.env.neon.local` (переменные Neon) в репозиторий не попадают.

Страница сама подхватывает новую версию: пока есть связь, файлы берутся с сервера, кеш служит запасным
вариантом для работы без интернета.

## Файл графика заказчика для тестов

Тесты импорта (`import.test.js`) читают настоящий «График производства работ» заказчика из
`fixtures/grafik-zakazchika.xlsx`. В репозиторий этот файл не выкладывается: это производственный
документ заказчика. Положите свой файл графика по этому пути — либо запросите исходный у команды
проекта. Остальные тесты (`site.test.js`) работают без него.
