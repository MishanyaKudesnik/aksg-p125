# АКСГ — техническая документация

**Проект:** P125 «Центр управления» — автоматизированный контрольно-сетевой график строительства
железнодорожной инфраструктуры.
**Заказчик:** ДКСС ОАО «РЖД». **Команда:** ШЦТ-211.
**Рабочий адрес:** https://aksg-p125.vercel.app
**Дата документа:** 26.11.2026

## 1. Что это такое

Система ведёт календарно-сетевой график стройки: план, факт, прогноз, подтверждения объёмов,
отчёты. Отличие от электронного журнала в том, что она **считает сама**: по фактическому темпу
прогнозирует дату окончания каждой работы, передаёт задержку по цепочке зависимостей и не даёт
записать объём без подтверждающего документа.

Работает в браузере на ноутбуке и планшете, **без интернета на участке** и с автоматической
отправкой правок, когда связь появится.

### Что умеет

| Блок | Содержание |
|---|---|
| КСГ | таблица работ: план, факт, статус, прогноз, оценка, зависимости |
| Расчёты | ожидаемый процент, прогноз окончания по темпу, каскад задержек, оценка «норма / риск / отклонение» |
| Пикетаж | слои работ по пикетажу, поперечник пути, продольный профиль, диаграмма «время–пикетаж», линейная схема |
| Графики | S-кривая освоения, диаграмма Гантта со связями, участки «ожидание против факта», отклонения по работам |
| Подтверждения | фото, акты, схемы, журналы, кадры с камер — с хешем SHA-256 и метаданными съёмки |
| Отчёты | технический и «простым языком», оба печатаются в PDF одной кнопкой |
| Роли | инспектор, руководитель, администратор |
| Офлайн | работа без связи, выгрузка правок в Excel, полевой пакет с фотографиями |
| Оборудование | приём сводок от камер и датчиков в очередь на проверку человеком |

## 3. Почему выбрано именно это

Здесь — обоснование каждого решения. Это тот раздел, который спрашивают на защите.

### 3.1 Почему без фреймворка (ни React, ни Vue, ни Angular)

**Решение:** обычные HTML, CSS и JavaScript, никакой сборки.

**Почему:**

1. **Нечему ломаться при передаче.** Проект уйдёт другой команде или в эксплуатацию заказчику.
   Фреймворк тянет за собой сборщик, сотни пакетов в `node_modules`, конфиги и версии, которые
   через год перестают ставиться. Здесь достаточно открыть файл в редакторе.
2. **Офлайн достаётся бесплатно.** Нет бандла — значит, оболочку целиком можно положить
   в кеш Service Worker девятью файлами и открывать без связи. С фреймворком пришлось бы
   настраивать сборку под офлайн отдельно.
3. **Скорость на планшете.** Инспектор работает в поле, связь там плохая. Весь интерфейс —
   151 КБ скриптов и 25 КБ стилей; сборка на фреймворке обычно весит заметно больше,
   и это прямо переводится в секунды ожидания.
4. **Размер задачи это позволяет.** Тут нет сложного состояния: одна страница, девять разделов,
   данные приходят одним объектом. Фреймворк решает проблему, которой у нас нет.

**Чем платим:** разметка собирается строками в шаблонных литералах, а не JSX. Для объёма
в 2300 строк это нормально; если интерфейс вырастет в несколько раз, переход на фреймворк
будет оправдан — расчётное ядро от этого не пострадает, оно отделено (см. 4.1).

### 3.2 Почему PostgreSQL, а не SQLite, MySQL или MongoDB

**Решение:** PostgreSQL.

**Почему:**

1. **Обещание по информационной безопасности выполняется базой, а не кодом.** В документе ИБ
   проекта записан неизменяемый журнал (append-only). У нас это **триггеры на уровне базы**:
   ```sql
   CREATE TRIGGER history_append_only BEFORE UPDATE OR DELETE ON history
     FOR EACH ROW EXECUTE FUNCTION aksg_append_only();
   ```
   Переписать историю не может ни приложение, ни администратор с прямым доступом к SQL.
   В MySQL это тоже возможно, но в SQLite и MongoDB такой защиты нет.
2. **Транзакции нужны по существу дела.** Сохранение графика — это одновременная запись
   в `works`, `history` и `audit`. Если упадёт на середине, график разойдётся с журналом.
   `BEGIN … COMMIT` закрывает вопрос.
3. **Числа без потерь.** Проценты и отметки профиля хранятся в `NUMERIC`, а не в плавающей
   точке. Для объёмов и отметок в метрах это принципиально.
4. **Несколько человек пишут одновременно.** SQLite при параллельной записи блокирует файл
   целиком. У нас инспекторы в поле, камеры, датчики — писать будут одновременно.
5. **Это стандарт в отрасли.** В ОАО «РЖД» PostgreSQL — обычная практика; при переносе
   в контур заказчика не придётся ничего менять.

**Почему не MongoDB:** данные у нас строго табличные и связанные (работа → подтверждение → файл),
нужны внешние ключи и транзакции. Документная база здесь только мешала бы.

### 3.3 Почему `pg` 8.13.1 — и почему это единственная зависимость

**Решение:** один пакет в `package.json`.

```json
"dependencies": { "pg": "8.13.1" }
```

**Почему:**

1. **`pg` — официальный драйвер PostgreSQL для Node.** Альтернатив по сути две: `pg`
   и ORM поверх него (Prisma, Sequelize, TypeORM). ORM мы не берём сознательно:
   - вся работа с базой у нас — это 30 запросов в `lib/db.js`, которые видно глазами;
   - ORM прячет SQL, а нам как раз нужно показывать на защите, что именно выполняется;
   - Prisma — это ещё и кодогенерация с отдельным движком, то есть новый шаг сборки.
2. **Версия зафиксирована точно, без `^`.** `"pg": "8.13.1"` вместо `"^8.13.1"` — на деплое
   ставится ровно та версия, на которой всё проверено. Никаких «у меня работало».
3. **Одна зависимость — это одна поверхность атаки.** Типовой проект на фреймворке тянет
   сотни пакетов, и каждый — чужой код в нашем контуре. У нас их ноль, не считая драйвера базы.
4. **Совместимость проверена на деле.** Один и тот же код работает и с локальной
   PostgreSQL 16.15, и с боевой 18.7 на Neon — без единой правки. Это и есть та самая
   сочетаемость: базу можно поднять где угодно, код не заметит разницы.

### 3.4 Почему SheetJS `xlsx` 0.18.5

**Решение:** библиотека лежит файлом в репозитории (`public/xlsx.full.min.js`), а не ставится из npm.

**Почему:**

1. **График заказчика приходит в Excel.** Настоящий «График производства работ» — это `.xlsx`
   с шапкой согласования, разделами и недельной сеткой. Без разбора xlsx проект бессмысленен.
2. **Одна и та же библиотека на сервере и в браузере.** Тесты читают файл-образец
   `fixtures/grafik-zakazchika.xlsx` тем же кодом, каким его читает инспектор. Если бы
   на сервере и клиенте стояли разные парсеры, расхождения ловились бы на защите, а не в тестах.
3. **Версия 0.18.5 — последняя, опубликованная в публичном реестре npm.** Дальше SheetJS
   перешёл на собственный реестр. Фиксация файлом в репозитории снимает зависимость от чужого хостинга:
   проект соберётся и через пять лет.
4. **Работает без интернета.** Файл лежит в кеше офлайн-оболочки, поэтому Excel собирается
   на планшете в поле, где связи нет.
5. **Грузится лениво.** 861 КБ подключаются только при первой выгрузке или импорте.

### 3.5 Почему Vercel и Neon

**Решение:** сайт на Vercel, база — Neon (PostgreSQL) через маркетплейс Vercel.

**Почему:**

1. **Нужен был публичный адрес, а не `localhost`.** Это было требование: показать работающий
   сайт, а не экран разработчика.
2. **HTTPS и домен из коробки.** Service Worker (офлайн) по стандарту работает только
   на HTTPS — без этого не было бы работы в поле.
3. **Деплой одной командой,** без настройки серверов: `vercel deploy --prod`.
4. **Neon рядом с Vercel.** База подключается одной переменной `DATABASE_URL`, которую Vercel
   прокидывает в функции сам. Ничего не настраивается руками, нечему рассинхронизироваться.
5. **Бесплатный тариф покрывает учебный проект целиком.**

**Чем платим, честно:** на бесплатном тарифе база засыпает без обращений, и первый запрос
после простоя идёт **15–20 секунд**, дальше — 0,7–0,9 с. Поэтому перед показом сайт
открывают заранее. Ограничение базы — 0,5 ГБ, отсюда сжатие фотографий и квота на вложения (см. 5.4).

**Ничто из этого не является замком.** Код — обычный Node и PostgreSQL, без API Vercel
и без расширений Neon. Переносится на внутренний сервер заказчика без изменений.

### 3.6 Почему графики нарисованы своими руками, а не Chart.js / D3 / ECharts

**Решение:** весь SVG пишется в коде проекта.

**Почему:**

1. **Нужных графиков в библиотеках нет.** Ни Chart.js, ни ECharts не умеют «время–пикетаж»,
   продольный профиль с подвалом отметок, поперечник пути и ленту слоёв по пикетажу.
   Их всё равно пришлось бы рисовать руками — только ещё и поверх чужого API.
2. **Офлайн.** Библиотеку с CDN в поле не подгрузить, а класть ещё 200–400 КБ в кеш
   ради четырёх диаграмм незачем.
3. **Печать.** Наш SVG попадает в PDF-отчёт как есть. Canvas-библиотеки (Chart.js) в печать
   отдают размытую картинку.
4. **Темы.** Цвета берутся из CSS-переменных, поэтому светлая и тёмная темы работают сами.
   С готовой библиотекой тему пришлось бы прокидывать отдельно.

### 3.7 Почему scrypt для паролей

**Решение:** `crypto.scryptSync` из стандартной библиотеки Node, соль 12 байт, хеш 32 байта,
формат хранения `s1$соль$хеш`.

**Почему:** scrypt — алгоритм, специально устойчивый к перебору на видеокартах, и он есть
в Node «из коробки», без внешнего пакета.

**Расхождение с документом ИБ, которое мы не скрываем:** там названы Argon2 или bcrypt.
Стойкость сопоставима, но формально это расхождение. Решается либо правкой документа,
либо переходом на bcrypt — тогда появится первая внешняя зависимость. Это записано
и в README проекта.

## 4. Как части связаны между собой

### 4.1 Расчётное ядро отделено от всего остального

`public/engine.js` — чистые функции без обращения к экрану и к базе:
расчёт графика, прогноз, оценка, пикетаж, S-кривая, классификация работ по слоям.

Этот же файл подключают **три потребителя**:

```
public/engine.js  ←── браузер    (<script src="/engine.js">)
        ↑
        └──────────── сервер     (lib/engine.js — одна строка: module.exports = require('../public/engine.js'))
        ↑
        └──────────── тесты      (require('./public/engine.js'))
```

Технически это сделано обёрткой UMD: файл работает и как `<script>`, и как модуль Node.

**Зачем так.** Инспектор без связи считает прогноз у себя на планшете; когда связь появится,
сервер пересчитывает то же самое. Если бы расчёт был написан дважды — на клиенте и на сервере —
цифры неизбежно разошлись бы. Здесь это **физически один и тот же код**, и тесты проверяют
именно его. Это главная причина, по которой весь проект на одном языке.

### 4.2 Поток данных

```
График заказчика (.xlsx)
        │  import-schedule.js + xlsx 0.18.5
        ▼
   engine.normalize ──► PostgreSQL (таблицы works / sections / history / audit)
        ▲                      │
        │                      ▼  readState()
   PUT /api/state         GET /api/state  ──►  браузер: S = {sections, works, evidence, profile}
        │                                            │
        │                                            ├─► engine.schedule / assess / curves
        │                                            ├─► экран: КСГ, графики, пикетаж, отчёты
        │                                            └─► localStorage (офлайн-копия)
        │
   правки инспектора ──► очередь в устройстве ──► отправка при появлении связи
```

### 4.3 Как решается конфликт правок

У проекта есть счётчик версии `projects.rev`. Браузер присылает ту версию, которую видел.
Если на сервере уже новее — ответ `409` и свежее состояние, правки инспектора при этом не теряются:
они остаются в очереди устройства и применяются поверх. Это называется оптимистичная блокировка,
и она здесь нужна потому, что одновременно пишут несколько инспекторов и оборудование.

### 4.4 Три уровня хранения — и почему их три

| Где | Что лежит | Зачем |
|---|---|---|
| PostgreSQL | весь график, подтверждения, файлы, журналы | единственный источник правды |
| localStorage | копия состояния и очередь правок | работа без связи, мгновенный старт |
| IndexedDB | фотографии, ещё не ушедшие на сервер | снимки не помещаются в localStorage |

Service Worker при этом кеширует **только оболочку** (9 файлов), а данные — никогда.
Правило «сначала сеть, при отказе кеш»: пока связь есть, человек всегда видит свежие данные,
а запросы к `/api/` вообще не кешируются, чтобы не подставить вчерашние цифры.

## 5. База данных

### 5.1 Таблицы

16 таблиц, 6 индексов.

| Таблица | Что хранит |
|---|---|
| `projects` | проект и счётчик версии `rev` |
| `sections` | участки: имя, пикетаж от и до |
| `works` | работы: план, факт, статус, источник, зависимости, пикетаж |
| `history` | **журнал изменений факта** (только дозапись) |
| `audit` | **журнал действий** (только дозапись) |
| `evidence` | подтверждения: акты, фото, схемы, журналы |
| `files` | вложения: содержимое, размер, SHA-256, когда и чем снято, архив |
| `profile` | продольный профиль: пикет, отметка земли, проектная отметка |
| `users`, `sessions`, `invites` | люди, входы, коды приглашения |
| `devices` | камеры и датчики, их ключи (в виде хеша) |
| `reports` | сводки от оборудования, ждущие проверки человеком |
| `batches` | загруженные полевые пакеты (защита от повторной загрузки) |
| `attempts` | счётчики для ограничения частоты запросов |
| `settings` | настройки проекта |

### 5.2 Что запрещено на уровне самой базы

- `history` и `audit` — триггеры запрещают `UPDATE` и `DELETE`. Проверено тестом:
  прямой SQL получает отказ `42501`.
- Плановые сроки нельзя сдвинуть без основания — проверка и в интерфейсе, и на сервере
  (сервер отвечает `400` и не меняет ничего).
- Удаления файлов в системе нет вообще: содержимое уезжает в архив, строка с хешем остаётся.

### 5.3 Миграции

Схема применяется при старте: `CREATE TABLE IF NOT EXISTS` плюс шесть `ALTER TABLE … ADD COLUMN
IF NOT EXISTS` для полей, добавленных по ходу работы (`file_id`, `sha256`, `taken_at`, `device`,
`archived_at`, `archive_ref`). Отдельного инструмента миграций нет и не нужно: база поднимается с нуля
одной функцией `init()`, повторный запуск безопасен.

### 5.4 Пределы по объёму

| Предел | Значение | Почему |
|---|---|---|
| Фотография | 1,2 МБ | на устройстве снимок жмётся до 900 КБ (1600 точек по длинной стороне) |
| Любой файл | 3,5 МБ | ограничение платформы на размер запроса |
| Все вложения проекта | 350 МБ (`FILES_QUOTA_MB`) | база бесплатного тарифа — 0,5 ГБ |

С 80 % заполнения система сама поднимает сигнал «Место в хранилище». Освобождение — архивом,
а не удалением.

## 6. Серверная часть

12 методов, каждый — отдельный файл в `api/`, каждый проверяет роль.

| Метод | Назначение | Кто может |
|---|---|---|
| `/api/auth` | вход, регистрация по коду, выход | все |
| `/api/state` | чтение и запись графика целиком | чтение — все, запись — инспектор и администратор |
| `/api/sync` | загрузка полевого пакета | инспектор, администратор |
| `/api/history` | хронология и список пакетов | все |
| `/api/file` | загрузка и выдача вложений, занятое место | выдача — все, загрузка — инспектор |
| `/api/profile` | продольный профиль | чтение — все, запись — инспектор |
| `/api/sensor` | приём сводок от камер и датчиков | по ключу устройства |
| `/api/review` | принять или отклонить сводку | инспектор, администратор |
| `/api/archive` | архив вложений: выгрузка, освобождение места, возврат | администратор |
| `/api/admin` | люди, роли, коды, устройства, журнал | администратор |
| `/api/backup` | резервная копия проекта | администратор |
| `/api/notify` | что требует внимания | все |

**Проверка прав — в одном месте** (`lib/http.js`, функция `need`), а не в каждом обработчике.
Забыть её невозможно: без неё метод просто не получит пользователя.

## 7. Безопасность

| Что обещано в документе ИБ | Как сделано |
|---|---|
| Целостность файлов по SHA-256 | хеш считается при загрузке, сверяется при **каждой** выдаче; не совпало — выдача останавливается (409) и пишется в журнал |
| Ограничение частоты запросов | 5 неверных попыток входа по логину и 20 с адреса за 15 минут, дальше отказ 429 на 15 минут |
| Неизменяемый журнал | триггеры в самой базе на `history` и `audit` |
| Резервное копирование | `GET /api/backup` — весь проект одним файлом, **без паролей** |
| Правка плана только с основанием | проверяется и в интерфейсе, и на сервере |
| Данные подрядчика «требует проверки» | сводки оборудования не становятся фактом сами, их принимает человек |

Дополнительно: сессии в HttpOnly-куке `SameSite=Lax` на 30 дней, `Secure` на боевом сайте;
заголовки `x-content-type-options: nosniff`, `x-frame-options: SAMEORIGIN`,
`referrer-policy: same-origin`; ключи устройств хранятся хешем и показываются один раз.

**Внешних сервисов в коде нет ни одного.** Уведомления — свои, от самого приложения.
Это проверяется отдельным тестом: он ищет в коде обращения наружу и падает, если они появятся.

## 9. Как запустить и как развернуть

### Локально

```bash
createdb aksg                      # нужен PostgreSQL 14 и новее
echo 'DATABASE_URL=postgres://localhost/aksg' > .env.local
npm install                        # поставится ровно один пакет
npm run dev                        # http://localhost:3000
npm test                           # 70 тестов
```

Первый зарегистрировавшийся становится администратором; дальше вход только по коду приглашения,
роль заложена в самом коде.

### На боевой адрес

```bash
vercel deploy --prod
```

Переменная `DATABASE_URL` прокидывается Vercel из Neon автоматически.
После выката надо поднять номер версии кеша в `public/sw.js` (`aksg-shell-vN`), иначе у тех,
кто уже открывал сайт, останется старая оболочка.

### В контур заказчика

Нужны только Node ≥ 22 и PostgreSQL. Ни Vercel, ни Neon в коде не упоминаются:
`api/*.js` — обычные обработчики `(req, res)`, их поднимает и `dev-server.js` на 47 строк.

## 10. Что сознательно не сделано

Честный список — его лучше назвать самим, чем услышать вопросом.

| Чего нет | Почему |
|---|---|
| BIM-модель и 4D | другой объём работ и другие данные; в чате проекта это признали отдельной задачей |
| Интеграция с системами ОАО «РЖД» | интегрироваться не с чем — данные передаются файлами |
| Мобильное приложение | сайт и так ставится на планшет ярлыком и работает офлайн |
| Кривые и геология на профиле | таких данных система не получает; рисовать «похоже на правду» нельзя |
| Argon2 или bcrypt | расхождение с документом ИБ, описано в разделе 3.7 |

## 12. Коротко, одним абзацем

Система написана на обычных HTML, CSS и JavaScript без фреймворка и без сборки; сервер —
Node.js ≥ 22, база — PostgreSQL (боевая 18.7 на Neon, локальная 16.15). Во всём проекте
**одна внешняя зависимость** — драйвер базы `pg` 8.13.1 с точно зафиксированной версией,
плюс библиотека `xlsx` 0.18.5, лежащая файлом в репозитории, потому что график заказчика
приходит в Excel. Расчётное ядро — один файл, который используют браузер, сервер и тесты,
поэтому офлайн и онлайн считают одинаково. Обещания по информационной безопасности выполняются
средствами самой базы, а не кодом приложения. Всё проверяется 70 автоматическими тестами
на настоящей базе. Проект не привязан к Vercel и Neon и переносится в контур заказчика
без изменений кода.
